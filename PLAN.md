# mwan3 — план задач

Обновлён: 2026-10-01

## Активное: фикс «интернет не отключается, пока доступен последний канал»

Проблема: при провале track-пингов mwan3 помечает интерфейс offline; если offline уходят все каналы политики, терминальное правило политики ставит метку `unreachable` (`ip rule` → EHOSTUNREACH) — трафик политики убивается, даже если линк физически жив. Кейс prod wwan: отельный апстрим роняет ICMP окнами по 15–60 с каждые 2–4 мин при стабильной WiFi-ассоциации (диагностика 2026-09-25, см. EchoVault `prod wwan флапает`).

Текущее состояние прода (проверено живыми окнами 2026-09-25 19:11–19:20 UTC):

| # | Факт | Источник |
|---|------|----------|
| 1 | Workaround Пилота: `default_rule_v4 → use_policy 'default'` — интернет LAN при offline последнего канала жив | конфиг `/etc/config/mwan3` |
| 2 | Цена: политика `ipv4_primary` без ссылок (0 references), mwan3 де-факто monitor-only, policy-switching мёртв | `iptables -t mangle -L mwan3_policy_ipv4_primary` |
| 3 | Рубильник жив, но не дотягивается: при offline policy-цепочка получает терминальный `MARK xset 0x3e00` (unreachable); правило `2001` (fwmark 0x100 → table 1) и table 1 при этом НЕ удаляются | дампы во всех состояниях mwan3track |
| 4 | IPv6 НЕ защищён: `default_rule_v6 → ipv6_primary` (tb64, `last_resort unreachable`) — при offline tb64 v6-трафик будет убит | конфиг |
| 5 | LAN-транзит и DNS через роутер в offline-окнах: 0 unreachable-отказов, только таймауты реальных потерь | наблюдатели с LAN |

### 1. Выбранное решение: sticky keepalive (правка кода в форке)

Требование Пилота: **последний рабочий канал не отключается независимо от прохождения проверок**. Сценарий на два канала: пинги пропали на первом → уход на второй; пинги пропали на втором → второй выключать нельзя.

Почему отвергнуты конфиг-варианты A1/A2 (`last_resort='default'`): они помечают `0x0` → main-таблица. При одном канале это спасает, но при двух main-таблица уводит в **мёртвый первый канал** — ровно тот случай, который требуется закрыть. `default` чинит только одноканальную конфигурацию.

Механика — три точки в `files/lib/mwan3/mwan3.sh`:

| # | Точка | Что делает |
|---|-------|-----------|
| 1 | `mwan3_keepalive_record()` — вызов из ветки `is_lowest` в `mwan3_set_policy` | Ветка `is_lowest` по построению означает «этот участник реально нёс трафик». Записывает в `$MWAN3_STATUS_KEEPALIVE_DIR/<policy>` две строки: имя участника и uptime на момент записи |
| 2 | `mwan3_keepalive_push()` — вызов в `mwan3_create_policies_iptables` сразу после `-F mwan3_policy_<p>`, до `case "$last_resort"` | Если запись есть, линк жив и запись не старше TTL — режет правило `-m comment --comment "keepalive <iface>" -j MARK --set-xmark <iface_mark>/$MMX_MASK` и **подавляет** терминальное правило `blackhole`/`default`/`unreachable` |
| 3 | `mwan3_keepalive_link_alive()` | Физ-сигнал: `carrier`=1 если файл есть; иначе `operstate`=up (у 6in4/wg файла `carrier` нет вообще) |

Ключевое: keepalive ставит **собственную метку участника**, а не `0x0`. `ip rule fwmark 0xe00/0x3f00 lookup 14` переживает уход трекера в offline, поэтому трафик идёт в таблицу именно того интерфейса, который последним работал.

Конфигурация: `mwan3.globals.last_resort_keepalive_ttl` (секунды, дефолт 180).

**Зачем TTL, если есть проверка линка.** Проверено на стенде: у мёртвого туннеля `6in4-tb70` (апстрим tb70 давно down) `carrier=1`, потому что 6in4 живёт, пока жив внешний линк `eth2`. Проверка линка не отличает «туннель умер» от «врут пинги». TTL — предохранитель: даже при идеально живом carrier запись протухает, `last_resort` возвращается, мёртвый участник не воскресает.

Отвергнутый вариант «читать operstate» для 6in4: `operstate=unknown` и у живых, и у мёртвых — сигнала не несёт.

### 2. Факты стенда `openwrt-dev` (проверено 2026-10-01)

| # | Факт | Следствие для фикса |
|---|------|----------------------|
| 1 | `default_rule_v4.use_policy='ipv4_primary'` — v4 в датапаф mwan3 (в отличие от prod) | Путь правится и проверяется на стенде |
| 2 | Мёртвые 6in4 (`6in4-tb69`, `6in4-tb70`) держат `carrier=1`, у мёртвых tb6/tb62/tb63/tb66 файла `carrier` нет вовсе, `operstate=down` | Нужен фолбэк на `operstate` **и** TTL |
| 3 | Живой wg31/tb65/tb67: `carrier=1 operstate=unknown` | Не полагаться на operstate, когда carrier есть |
| 4 | Имена цепочек mwan3 < 29 символов (`mwan3_policy_` = 13) | В тестах/скриптах — короткие имена политик |
| 5 | `config_load` живёт в `/lib/functions.sh`, `network_get_device` — в `/lib/functions/network.sh`; `jshn.sh` на этом образе только JSON | Скрипты проверки обязаны sourcing-ить оба |
| 6 | 7+ IPv6-политик, большинство `last_resort='unreachable'`, многие single-member | Ровно тот класс, который keepalive и защищает |

### 3. Тесты (TDD)

`tests/test_policy_keepalive.sh`, 9 кейсов, подхватывается `tests/run_tests.sh` по маске `test_*.sh`. Harness — bash + моки `tests/mocks/bin` (iptables/ip6tables/iptables-restore пишут в лог), библиотека mwan3 сорсена напрямую.

| # | Кейс | Что фиксирует |
|---|------|---------------|
| 1 | online lowest member recorded | рабочий участник попадает в sticky-запись |
| 2 | all offline, device alive | **инвариант**: `keepalive <iface>` есть, `unreachable` отсутствует |
| 3 | device gone | честная смерть: запись удаляется, `unreachable` возвращается |
| 4 | нет `carrier`, `operstate=up` | фолбэк читает устройство как живое |
| 5 | нет `carrier`, `operstate=down` | фолбэк читает устройство как мёртвое |
| 6 | нет записи | терминальный `unreachable` сохраняется (upstream-поведение не сломано) |
| 7 | двухканальная последовательность | wwan работает → пинги падают → wan работает → пинги падают → **остаётся wan** (сценарий Пилота целиком) |
| 8 | запись старше TTL | протухает, `last_resort` возвращается, файл записи удалён |
| 9 | запись внутри TTL | keepalive держится |

Замечания по harness: `set -e` **не используется** — код mwan3 написан под `/bin/sh` и не errexit-safe (`mwan3_set_policy` снимает статус голым `[ ... = "online" ]`), errexit убил бы прогон на легитимном «интерфейс offline». `MWAN3_SYSFS_NET` сделан переопределяемым ради мока sysfs.

Проверено: на немодифицированном форке — **3 passed, 6 failed**; с фиксом — **9 passed, 0 failed**. Полный сьют `wsl bash tests/run_tests.sh` — 27 тестов, все зелёные.

### 5. Верификация на стенде (выполнена 2026-10-01)

Библиотека залита на `openwrt-dev` (`/lib/mwan3/{mwan3.sh,common.sh}`), бэкапы оригиналов — `/tmp/{mwan3,common}.sh.orig`. Проверка шла на **синтетической** политике `zzka`, чтобы не трогать живые цепочки; после прогона цепочка и запись удалены.

| # | Проверка | Результат |
|---|----------|-----------|
| 1 | запись `tb70` (6in4, `carrier=1` при мёртвом туннеле) | режется `--comment "keepalive tb70" -j MARK --set-xmark 0xe00/0x3f00`; `ip -6 rule fwmark 0xe00/0x3f00 lookup 14` существует → датапаф сходится |
| 2 | запись `tb70` старше 3600 с | запись удалена, терминальный `unreachable` возвращён |
| 3 | запись `tb6` (нет `carrier`, `operstate=down`) | запись удалена, `unreachable` |
| 4 | живая политика `ipv4_primary` | цепочка пересобрана как обычно, запись `wwan` создана |
| 5 | TTL: дефолт 180 → 100 с держит / 300 с протухает | подтверждено |
| 6 | TTL `=30` → 10 с держит / 100 с протухает | подтверждено |
| 7 | TTL `=600` → 500 с держит | подтверждено |

Стенд после прогона: синтетических цепочек нет, `mwan3_policy_ipv4_primary` = `wwan 1 1 → 0x100/0x3f00`, ping 1.1.1.1 — 0% потерь.

**Прод не тронут** (прямое указание Пилота «роутер не трогай»): прод-роутер только читался.

### 6. Верификация на prod (когда будет дана команда)

Наблюдатели ≥30 мин (≥5 offline-окон): роутер — `mwan3 status` + `nft list table ip mangle` на переходах + `ip rule`; наблюдатель с LAN — `curl -4 https://1.1.1.1` и `dig @192.0.2.1` каждые 3 с. Плюс принудительный прогон: `uci set mwan3.globals.last_resort_keepalive_ttl` не трогать без нужды; для проверки отката — `kill -STOP` трекера или правка `track_method`.

### Риски и ограничения

| # | Риск | Обработка |
|---|------|-----------|
| 1 | 6in4/wg-туннель с `carrier=1` при мёртвом апстриме продержит политику до TTL | TTL 180 с — намеренная граница; короче нельзя (окна флапа 15–60 с + детект ~20–25 с), длиннее — лишняя задержка отказа |
| 2 | `carrier=1`, но трафик не идёт (туннель жив, апстрим мёртв) → тихие таймауты вместо unreachable | Это ровно то поведение, которое заказано: канал считается рабочим, пока нет физического отказа |
| 3 | Keepalive подавляет терминальное правило → при неучтённом сбое нет ICMP unreachable для диагностики | Страница `mwan3 status` остаётся, `LOG info` пишет протухание; в `/var/run/mwan3/keepalive/<policy>` видно, кого держим |
| 4 | Тест-гард — кандидат в upstream PR | Отдельное решение Пилота; в скоуп фикса не входит |
| 5 | На стенде оставлен пропатченный `/lib/mwan3` | Откат — команда из таблицы Rollback, строка 1 |
